### 實戰踩出來的規則（這些是別人用正式區換來的，不要再撞一次）

1. **會計科目不可以手動送。** 手動塞 `ACCOUNT_NO_INV=1311` / `LEVEL_CODE_INV=1143`
   （即使抄自正式區現有有效料號）會被判「存貨/費用科目設定必需為存貨類科目」。
   正確做法是**只送 `ACCOUNT_FLAG=Y`，讓 ARGO 依料件類別自動帶科目**。
2. **科目報錯的真正根因是類別衝突，不是科目本身。** 當初 `PRODUCT_CATEGORY='S'`，
   而 BOMF008 裡類別 S 定義為「代工類·費用類=Y」，與送出的 `EXPENSE_FLAG=N` 互斥，
   ARGO 卻報成科目錯誤。改成類別 `O`（客供料代工·製成品·非費用）就通了。
   **料號開頭字母必須與 PRODUCT_CATEGORY 一致，且要符合 BOMF008 對該類別的定義。**
3. **有一批欄位送了會被 `invalid column:` 直接拒收**：
   `OLD_VER, OLD_PART, MRP_FLAG, MPS_FLAG, LOT_NO_FLAG, LOT_SIZE_FLAG,
   NO_PICKING_FLAG, CFV_FLAG, ALLOW_FLAG, STD_MFG_MINUTES`
   —— 注意 **`LOT_NO_FLAG` 在這裡是拒收欄**，批號控管要送的是 **`LOT_NO_CONTROL`**。
4. **必填**：`ACCOUNT_USER`（審核人員工號）、`VALIDDATE`（生效日 `YYYY/MM/DD`）。
5. **只新增不更新。** 重送已存在料號回 `ORA-00001 (MBP_PK)`，送前必須先查主檔跳過。
6. **判成功不能只看 `STATUS=1`。** `RESULT` 只回檢核失敗列，而且**會累積前幾次的殘留**；
   正確判法是「該 PART 有沒有出現在 ERROR_CODE 裡」，再加一次 `MM_BOM_PART` 回查。
7. **`PRODUCT_CATEGORY_2`（小類）必須是 BOMF008 裡已建的有效值**，不存在就擋。
   當初 OSSC 是 Snow 在 BOMF008「料件小類」分頁手動建的。

## 二之二、⚠ 這推翻了目前申請單的三個地方

上週做的申請單，有三處與 IFAF007 的實際要求對不上，**接寫入之前必須先修**：

| # | 現況 | IFAF007 實際要求 | 怎麼改 |
| --- | --- | --- | --- |
| 1 | 申請單收集並鎖定「存貨科目層級 / 存貨會計科目」兩欄，本來打算照抄進 ARGO | **這兩欄手動送會被擋**，必須讓 ARGO 依類別自動帶 | 兩欄改為「**僅供核對參考**，不寫入 ARGO」。畫面保留（建檔人員仍要看），但 payload 不帶，只帶 `ACCOUNT_FLAG=Y` |
| 2 | 欄位叫 `lot_no_flag`（對應查詢用的 `MM_BOM_PART.LOT_NO_FLAG`） | 寫入時 `LOT_NO_FLAG` 是**拒收欄**，要送 `LOT_NO_CONTROL` | 寫入時做欄名映射，資料庫欄位不動 |
| 3 | 申請單只收 11 個 ERP 設定欄位 | 實際要送約 **40 個欄位**（大量旗標與成本欄） | 缺的那些不該讓申請人填，由**大類對應的 `BASE_FIELDS` 樣板**補齊 |

第 3 點是最大的新工作量：`create_o_parts.py` 那組 `BASE_FIELDS` 是**為 O 類代工件特化**的
（`PRODUCED=Y`、`LEADTIME_FLAG_SUBTYPE=MO`、`BOM_TYPE=M`…）。EIP 申請單支援
M / W / P / C / S / A / O 七個大類，**每一類都要有自己的一組樣板，而目前只有 O 類經過正式區驗證**。

M/W（採購材料）、C（採購成品）、S/A（費用類）的旗標組合必須各自在測試區驗過才能開放。
這也是分階段的天然切點——**先開放已驗證的類別，其餘逐類解鎖**。

## 三、流程設計

### 狀態機

```
  draft ──送出──▶ pending ──主管認領──▶ reviewing
                    │                      │
                    │                 ┌────┴────┐
                    │              核准│         │退回
                    │                 ▼         ▼
                    │             approved   rejected ──救回──▶ pending
                    │                 │
                    │            （寫入 ARGO）
                    │                 ▼
                    │              creating
                    │            ┌────┴────┐
                    │         成功│         │失敗
                    │            ▼         ▼
                    └────────  created   failed ──修正後重試──▶ approved
```

現況只有 `pending / created / rejected` 三態。新增 `reviewing`（誰在看，避免兩個主管重工）、
`approved`（審過了但還沒寫）、`creating`、`failed`。

**為什麼要把 approved 和 created 分開**：審查與寫入是兩件事。寫入會失敗（ARGO 連不上、
欄位被擋、編碼在審查期間被別人佔用），失敗時這張單必須停在「已核准但沒建成」而不是退回
重審——主管的判斷沒有錯，錯的是寫入，不該讓他再審一次。

### 審查頁長什麼樣

主管打開一張申請單，一個畫面看完三件事：

**① 申請內容**（唯讀，帳務欄位已鎖定）

**② 系統預檢結果**——這是「輕鬆審查」的關鍵，主管不該自己去 ARGO 查

| 檢查 | 做法 | 擋不擋 |
| --- | --- | --- |
| 建議編碼是否已存在 | `getPartTemplate(編碼)` 查 ARGO | 🔴 硬擋 |
| 同次類別有沒有名稱高度相似的品項 | `searchParts` 取同 `PRODUCT_CATEGORY_2`，比對品名 | 🟡 警示，主管判斷 |
| 編碼前綴是否符合大類 | 第一碼＝`PRODUCT_CATEGORY` | 🔴 硬擋 |
| 必填欄位是否齊全 | 對照 IFAF007 必填清單 | 🔴 硬擋 |
| 帳務欄位是否與引用來源一致 | 與 `template_part` 逐欄比對 | 🟡 警示 |
| 單位是否在 ARGO 既有單位清單內 | 查 `mm_bom_part_units` | 🔴 硬擋 |

「🟡 相似品項」那條最值錢——重複編碼的真實成因通常不是打錯字，而是
**不知道已經有一個幾乎一樣的品項**。把相似品直接列在主管眼前（含編碼、品名、
最近用在哪張單），比要求他自己想起來可靠得多。

**③ 最終編碼**

申請人填的是「建議編碼」，最終由主管決定。系統依大類＋次類別查 ARGO 現有最大流水號 +1
產生候選值，主管可改。**送出寫入前會再查一次重複**（審查到按下送出之間可能有人佔用）。

### 批次審查

清單頁可勾選多張 → 「批次核准」。但**核准是批次的，寫入是逐筆的**：

- 批次核准只改狀態，不碰 ARGO，風險低
- 寫入排隊逐筆送，任一筆失敗不影響其他筆，各自標 `failed` 並記下原因
- 全部跑完給一張結果表：成功幾筆、失敗幾筆、失敗原因分別是什麼

不做「批次一次送一個大陣列給 ARGO」——那樣一筆格式錯可能整批退，而且分不出是哪筆的問題。

## 四、安全機制：五層

寫進 ERP 的東西刪不掉（料件主檔只能作廢不能刪），所以防線要疊。

### 第 1 層　申請端：帳務欄位鎖定 ✅ 已完成
庫存類型、成本類別、費用類、存貨科目層級、存貨會計科目唯讀，值由引用品項或大類預設決定，
後端不信前端送的值。

### 第 2 層　預檢：送審前自動跑
上表那六項。硬擋項目沒過就不能進入「核准」按鈕。

### 第 3 層　人審：權限分離（Snow 2026-09-16 定案）
- 新增權限鍵 **`product_dev_approve`**，與現有 `product_dev`（申請）分開，
  **在後台「團隊管理」勾選發放**（`app/admin/team/page.tsx` 權限清單加一項），與其他權限同一套做法
- **一個人核准即可**，不做雙人會簽——多一關只會讓單積著，而防錯主要靠第 2 層預檢與第 4 層回查
- **申請人不能核准自己送的單**（後端檢查 `requester_email !== approver_email`）。
  這條與「單人核准」不衝突：擋的是自審，不是要求兩個人簽

### 第 4 層　寫入：乾跑 → 單筆 → 立即回查
沿用庫存開帳那套已驗證的四步：

1. **送出前先查主檔**：IFAF007 只新增不更新，重送已存在料號會 `ORA-00001`。
   這一步同時擋掉「審查期間編碼被別人佔用」
2. **乾跑**：組好 payload 但不送，畫面顯示「將送給 ARGO 的完整 40 個欄位」，主管確認
3. **送出單筆**：一次一筆，不批次
4. **看 `ERROR_CODE` 判成功，不看 `STATUS`**：`RESULT` 只回檢核失敗列且會累積前幾次殘留，
   `STATUS=1` 不代表這一筆成功。要檢查「這個 PART 有沒有出現在錯誤列裡」
5. **再回查一次 `MM_BOM_PART`** 確認該編碼真的在正式表出現 —— 雙重確認，因為第 4 步
   靠的是「沒有錯誤」這種否定證據，第 5 步才是肯定證據
6. **任一步沒過就標 failed**，不標 created，ARGO 原始回應完整留在軌跡裡

### 第 5 層　事後：對帳
每日排程比對「EIP 標記 created 的編碼」vs「ARGO MM_BOM_PART 實際存在的編碼」，
有落差就 LINE 通知。做法與 `void-shipped-scan` 相同。

> 為什麼還要對帳：第 4 層已經回查過了，但 ARGO 的介面表有「延遲過帳」的可能
> （IFAF083 就需要另外呼叫 `P_IMPORT_IFAF083` 觸發）。對帳是最後一道網。

## 四之二、審查頁放在哪

**建議：首頁「商品開發」卡片 → 抽屜裡第四張卡「品項編碼審查」，路徑 `/product-dev/item-approval`**

```
首頁
 └─ 商品開發（卡片，右上角紅點顯示待審張數）
     ├─ 📥 下載物料清單
     ├─ 📦 下載生產品項
     ├─ 🆕 申請新品項編碼        ← 現有，誰都能進（product_dev）
     └─ ✅ 品項編碼審查 [5]      ← 新增，只有 product_dev_approve 看得到
```

理由：

1. **語意連貫**。申請與審查是同一件事的兩端，放同一個抽屜，不必為了審查另闢一個頂層位置。
2. **沒權限的人畫面完全不變**。這張卡依 `product_dev_approve` 顯示，商開看不到，
   不會出現「點進去說你沒權限」的死路。
3. **紅點才是真正解決「輕鬆」的地方**。首頁卡片已經有現成的徽章機制
   （採購專區 `purchasingDue` 那顆紅色數字），沿用即可。主管一登入 EIP 就看到
   「商品開發 ⑤」，不用記得要去看——審查會不會積著，關鍵從來不是審查頁好不好用，
   而是**會不會忘記有東西要審**。

### 順帶要釐清的：兩頁的分工

現在 `/product-dev/item-request` 一頁包辦「填申請」和「申請進度＋處理動作」，
建檔人員就在那個清單上回填編碼／退回。加了審查頁之後要切開，否則兩個地方都能處理會亂：

| | 申請頁 `/product-dev/item-request` | 審查頁 `/product-dev/item-approval` |
| --- | --- | --- |
| 誰進 | `product_dev`（全體商開） | `product_dev_approve`（主管） |
| 看得到 | **自己送出的**申請與進度 | **所有人**的待審申請 |
| 能做 | 填新申請、看自己的軌跡 | 預檢結果、核准／退回、決定最終編碼、寫入 ARGO |
| 處理動作 | ❌ 移走 | ✅ 集中在這裡 |

**其他備選（現在不做，記著）**：若日後請購簽核、報價審核也要進 EIP，
再把這頁升格成獨立的「簽核中心」`/approvals`，品項編碼是其中一個模組。
現在只有一種待審事項，先不做這層抽象。
