# 規劃書：採購專區來源單號 → 訂單詳情＋示意圖連結

日期：2026-08-31
狀態：**已實作**（2026-09-02，分支 feat/purchasing-so-details-print-index）。
實際落地與本規劃的差異：Snow 拍板「只做採購專區、圖不出內網」後，發現 argo-tool
早已內建 NAS 示意圖 API＋縮圖引擎＋EIP SSO（bardshop-argo.com，HTTPS）——
方案二不必自建橋接服務，直接沿用；且 HTTPS→HTTPS 無 Mixed Content 問題，
縮圖得以**內嵌**在 EIP 視窗（比本文預期的「開新分頁」更好）。
索引（掃描器＋print_asset_index）依第四節實作，供 📷 徽章張數用。
流程原則：一律先開本地分支、本地測試完畢、開 PR，才進 main（不直接推 main）。

## 一、需求

採購專區（`/purchasing`）追蹤列表的「SO單號」欄目前是純文字。要做到：

1. **點 SO 單號 → 跳出訂單詳情**（品項、數量、交期、備註等）
2. **從詳情連到該訂單的示意圖**。示意圖自 2026 年 8 月起統一放在「#」下的「印刷資料夾」內

## 二、現況盤點（已查證）

### 程式面

| 項目 | 現況 |
| --- | --- |
| SO 欄位 | 純文字（`app/purchasing/page.tsx`，桌機與精簡模式各一處） |
| 訂單詳情視窗 | **已有現成元件 `components/SoOrderModal.tsx`**，出單表、ERP 同步區、集合單三頁都在用，支援 `liveRefresh`（即時回 ARGO 撈最新）。第 1 項需求＝掛上這個元件，半天內含測試可完成 |
| 檔案/圖片服務 | EIP 目前**沒有**任何讀取檔案系統或提供圖檔的基礎設施 |

### 檔案面（已實地確認，2026-08-31 抽查 4 張單）

位置：`\\192.168.1.141\ro排單圖庫\RO\`，目前 38 個訂單資料夾。實際結構：

```
RO\
  SO260817009 愛放客股份有限公司\          ← 訂單資料夾：「訂單號＋空格＋客戶名」
    #1壓克力色紙 15cm 10cm 2mm\           ← 品項資料夾（#行號＋品名，但≠每張單都有）
      印刷\
        SO260817009【6650 CCD】…3pcs.eps      ← 印刷原稿（56MB）
        【商品示意圖】SO260817009_A.png        ← 示意圖（3MB）
      美編\
        【商品示意圖】SO260817009.pdf          ← 示意圖 PDF（7MB）
    原檔\
```

**穩定可依賴的兩條規則**：
1. 訂單資料夾一律以**訂單號開頭**（SO／SOA 都驗證過）→ 單號比對可靠
2. 示意圖檔名一律 **`【商品示意圖】訂單號[_後綴]`**（png/jpg/pdf）→ 可準確挑出「能預覽的圖」，與 56MB 的 eps 原稿區分

**不穩定、不能依賴的**：品項層資料夾格式不一——有的是 `#1品名`、有的直接用品名（`滑鼠墊`）、單一品項的單甚至沒有品項層。**索引只做到訂單層級，不做行級對應**。

| 項目 | 現況 |
| --- | --- |
| 檔案格式 | png／jpg／pdf（示意圖，1–7MB，可預覽）＋ eps（印刷原稿，可達 56MB，只列不預覽） |
| 時間範圍 | 8 月起才統一歸檔；**8 月以前的訂單沒有示意圖**，介面查無時不顯示徽章即可 |
| 其他共享 | 同 NAS 另有 `集單`、`常平廠發單明細` 等資料夾，本次不納入，日後可用同一套索引擴充 |

### 部署面（這是整個設計的核心限制）

EIP 部署在 **Vercel（雲端）**，示意圖在**公司內網 NAS**。

```
使用者瀏覽器 ──HTTPS──> Vercel（EIP）        ← 摸不到 NAS
     │
     └────內網────> \\192.168.1.141\ro排單圖庫  ← 只有在公司才通
```

兩個硬限制：

1. **Vercel 永遠連不到 `192.168.1.141`**。任何「伺服器端讀圖」的做法都不可行，除非先把圖（或索引）送出內網。
2. **瀏覽器禁止 HTTPS 頁面開 `file://` 連結**。「直接放個 UNC 連結」點了不會有反應，這條路在技術上就是死的。

所以「連到示意圖」必然是以下三選一：給**路徑**（人工貼到檔案總管）、經過**內網橋接服務**、或把圖**搬上雲**。

## 三、方案比較

**共同前提：三個方案都需要「索引」。** 不管最後怎麼開圖，EIP 都得先知道「這張 SO 有沒有圖、在哪」。做法：公司內一台常開的電腦跑排程掃描器，掃 NAS 的 ro排單圖庫，把 `SO單號 → 檔案路徑` 寫進 Supabase 新表 `print_asset_index`。Vercel 查表就知道有沒有圖。這部分是固定成本，約半天。

### 方案一：索引＋複製路徑（零基建）

EIP 顯示「📷 示意圖 N 張」，點開列出檔名與完整 UNC 路徑，附「複製路徑」按鈕；使用者貼到檔案總管開啟。

| | |
| --- | --- |
| 優點 | 不需要任何新伺服器；權限沿用 NAS 現有設定；一天內可上線 |
| 缺點 | 兩步操作（複製→貼上），不能直接預覽；**不在公司內網的人完全開不了** |
| 適合 | 最快讓功能存在，先驗證「索引能不能對得準」 |

### 方案二：內網橋接預覽（建議的第二階段）

在公司內一台常開機器跑小型 HTTP 服務，提供 `GET /prints/{so}` 縮圖與原圖。EIP 的示意圖清單直接顯示縮圖、點了新分頁開原圖（`http://內網IP:埠/...`，HTTPS 頁面開新分頁導向 HTTP 是允許的，內嵌才會被擋）。

**現成的落點：`bardshop-argo-tool`（FastAPI，D:\AI\argo-tool）**。它已經在跑每日排程、而且已內建與 EIP 的 iframe+token 整合骨架——等於驗證機制不用從零做。

| | |
| --- | --- |
| 優點 | 點了就看到圖，體驗完整；圖不出內網（機密性最好）；沿用既有服務與 token 機制 |
| 缺點 | 依賴那台機器常開；**不在內網的人一樣看不到**（連結會逾時）；要多維運一個端點 |
| 工作量 | 1–2 天（縮圖產生、token 驗證、EIP 端 UI） |

### 方案三：縮圖上雲（有遠端需求才做）

掃描器產生壓縮縮圖（每張約 100–300KB）上傳 Supabase Storage，EIP 從雲端直接顯示。

| | |
| --- | --- |
| 優點 | 任何地點、手機都能看；不依賴內網 |
| 缺點 | **設計圖離開公司**（機密性決策，要你拍板）；儲存量與流量成本；同步延遲；原圖仍要回內網拿 |
| 適合 | 出現「業務在外面要看圖」的真實需求之後 |

### 建議路線

```
第 1 步  訂單詳情：SO 欄掛 SoOrderModal            （半天，無風險，可獨立先做）
第 2 步  索引掃描器 ＋ 方案一（路徑複製）            （一天）
第 3 步  方案二（argo-tool 橋接預覽）               （1–2 天，第 2 步驗證對得準之後）
     ─── 方案三不排程，需求出現再議 ───
```
※ 原「第 0 步：確認資料夾結構」已於 2026-08-31 完成，結論寫入第二節。

## 四、設計細節（採建議路線時）

### 索引表 `print_asset_index`

```sql
create table print_asset_index (
  id          bigserial primary key,
  so_no       text not null,          -- 從路徑抓出的訂單號（SO/RO/SOB…）
  rel_path    text not null,          -- 相對 ro排單圖庫 根目錄的路徑
  file_name   text not null,
  ext         text,                   -- jpg/png/pdf/ai/psd…
  size_bytes  bigint,
  file_mtime  timestamptz,
  scanned_at  timestamptz default now(),
  unique (so_no, rel_path)
);
```

### 掃描器（跑在公司常開機）

- 排程每小時；比對 `mtime` 做增量，改名/刪除以「本輪沒掃到就清掉」處理。目前僅 38 個資料夾，全量掃也只是秒級
- **比對規則**（依實地確認的結構）：
  - 訂單關聯＝**第一層資料夾名的開頭訂單號**（`^(SO|SOA|SOB|RO)[\d-]+`），不靠檔名逐一比對
  - 示意圖標記＝檔名以 `【商品示意圖】` 開頭且副檔名 png/jpg/pdf → `is_preview = true`
  - eps／ai／psd 等原稿照樣入索引（給「複製路徑」用），但 `is_preview = false`，永不預覽、不經橋接傳輸
- 提供 `--dry-run` 印出「會建立哪些關聯」供上線前人工核對
- 掃不到、NAS 斷線 → 保留舊索引不清空（沿用「回空陣列不覆蓋」的護欄原則）

### EIP 端

- SO 欄變可點：點文字 → `SoOrderModal`；旁邊若索引有資料，顯示 `📷N` 小徽章
- 徽章點開：檔名清單＋複製路徑（第 2 步）→ 之後升級為縮圖牆（第 3 步）
- 查無圖（含 8 月前舊單）：不顯示徽章即可，詳情視窗內不需要「查無示意圖」的噪音
- 元件做成共用：之後出單表、業務查詢要掛同一顆徽章時直接重用

## 五、動工前必須由你確認的事

1. **掃描器跑哪台機器**：建議跟 argo-tool 同一台（既有排程、常開）。確認那台連得到 `\\192.168.1.141\ro排單圖庫` 且有讀取權限

3. **範圍**：這次只做採購專區，還是出單表、業務查詢一次掛齊？（建議先採購專區，元件做成共用，之後掛別頁是小事）
4. **歸檔紀律**：這套機制的準確率完全取決於美編照規矩把資料夾命名為「訂單號＋客戶名」。目前抽查 4 張全部合規，但 `RO` 下也有 `Koala`、`7151 RL測試圖` 這類無單號資料夾（索引會自動略過，不是錯誤）——要不要順勢跟美編約定命名規範，由你決定

## 六、風險與地雷

| 風險 | 對策 |
| --- | --- |
| 資料夾沒照「訂單號＋客戶名」命名 | 索引對不到該單（已抽查 4 張全合規；無單號的雜項資料夾自動略過）。長期靠命名規範維持 |
| 品項層結構不一（#1／品名／無品項層） | 索引只做訂單層級，不做行級對應——結構怎麼變都不影響 |
| 中文檔名／特殊字元 | 掃描器與橋接服務全程 UTF-8，上線前拿實際檔案測 |
| NAS 資料夾日後重整 | 索引每小時重建，路徑變了下一輪自動修正 |
| 橋接機器關機 | 縮圖開不出來，但索引還在（退化成方案一的路徑複製，不是全壞） |
| 大檔（ai/psd 數百 MB） | 只列檔名與路徑，不做預覽、不經橋接傳輸 |
| 追加單/改圖多版本 | 全部列出、依 mtime 排序，最新在前；不做「哪張才是對的」的判斷 |

## 七、明確不做的事

- 不在 Vercel 上直連 NAS（做不到）
- 不把原圖上雲（只有縮圖在方案三才考慮，且需你拍板）
- 不動採購專區既有欄位與其他篩選
- 不做圖片上傳/管理功能——EIP 只讀，圖的管理仍在檔案總管
