# ERP 同步區：訂單修改紀錄、工單對位體檢

發布日期：2026-08-26
範圍：ERP 同步區（`/admin/argoerp/erp-sync`、`/argo-db`）新增兩個分頁。既有九個分頁與「啟動全表同步」完全不動，屬純新增。

---

## 一句話

現在看得到「誰在幾點把哪張單的哪個位置從什麼改成什麼」，而且會告訴你這次改動有沒有影響到已經發下去的工單、該通知哪個單位；另外多一張體檢表，列出目前所有「工單上印的行號已經對不到訂單」的製令。

## 公告欄白話版

> 📋 **ERP 同步區新增兩個分頁**
>
> **1. 訂單修改紀錄** — 每 5 分鐘自動偵測銷售訂單的異動，逐筆記錄：
> - 幾點幾分、工號姓名（**實際動手改的人**，不是訂單掛名業務）
> - 改了哪張單的第幾行、哪個欄位、從什麼改成什麼
> - 這一行**發單到哪了**（未發單／已開製令／已發單／已備料／生產中）
> - 會影響哪些單位、**該通知誰**
>
> **2. 工單對位體檢** — 工單號末兩碼記的是「發單當下這個品項排在第幾行」。訂單事後被插入或刪除品項，行號會整批位移，但已印出去的工單還停在舊行號，現場拿工單去對訂單就會對到別的品項。這一頁列出目前所有對不上的工單。
>
> ⚠️ **請注意：訂單一旦發過單，就不要再插入或刪除品項行。** 需要增減請改用追加訂單，或與生管確認後重新發單。現場核對一律以工單上的**品項料號**為準，不要用行號。

## 分頁一：訂單修改紀錄

### 資料從哪來

不新增任何偵測機制。每 5 分鐘的增量同步一直在寫 `erp_change_log`（含 before／after／變動欄位），這裡只是把它翻成人話。**本分頁不觸發同步、不寫任何資料。**

`erp_change_log` 沒有「誰改的」，所以即時向 ARGO 補查：

- `PJ_PROJECT` / `PJ_PROJECTDETAIL` 的 `UPDATE_BY`／`UPDATE_DATE`（**行層級、精確到秒**）
- `HR_PERSONNEL` 的工號 → 姓名

`UPDATE_BY` 是實際動手改的人，與 `SALES_ID`（訂單掛名業務）不一定相同——實例：SO260824012 掛名業務林盈劭，實際改單的是張宜庭。兩者不同時介面會並列顯示。

### 發單狀態與影響單位

| 狀態 | 判斷依據 |
| --- | --- |
| 未發單 | 找不到對應製令 |
| 已開製令 | `erp_mo_lines` 有對應 |
| 已發單上傳 | `argoerp_mo_upload_log` |
| 已備料 | `argoerp_material_prep_log` |
| 生產中 | `sara_wip_schedule` 有 running／pause 的工序 |

影響單位優先用塔台實際排程的工作中心（依 `job_sequence` 排序）；塔台還沒有這批時，退回用料號的標準途程（`item_routes` → `route_operations`）預測並標示「預估」。

### 該通知誰

依「改了什麼」加上「有沒有發單」判定：

- **財務部門**：單價、幣別、匯率、發票型態、客戶代號——只影響帳務，不影響生產
- **美編部門**：尚未發單。工單還沒到現場，不影響生產，但美編可能已依舊內容作業
- **全廠**：已發單後才改。交期、交貨地址、包裝另註明「含包裝出貨都需知悉」
- 新增／刪除品項在已發單時也是全廠，因為**插行會讓後面品項的工單行號失效**

### 介面

- 一次操作（同一人、同一張單、同一秒）併成一組；超過 4 筆變更自動收合，另有「全部展開／收合」
- 單頁最多 100 條，以「一次操作」為切割單位，同一次改單不會被拆到兩頁
- 「⚠ 只看已發單後才改」篩選，按下後依危險程度排序
- 訂單號旁若出現紅色「工單行號失效 N」，點擊會跳到「工單對位體檢」並自動篩選該訂單
- 可匯出 CSV

## 分頁二：工單對位體檢

回答的是「現在」的問題：有哪些工單的行號已經對不到訂單。

**為什麼獨立成一頁而不是在修改紀錄加欄位**：錯位是「現況」不是「事件」，多半由好幾週前的改單累積造成，不會出現在近幾天的修改紀錄裡（本次發現的 7 筆，製令日期橫跨 5/13～7/2）。

分兩類：

- **行號跑掉**：品項還在同一張訂單，但換到別的行了。工單要做的東西沒錯，錯的是上面印的行號
- **品項已不在單上**：這張工單要做的品項，訂單上已找不到（被改成別的料號或整行刪掉）

依訂單分組，危險的排前面，可只看「已發到現場」的，可匯出 CSV。

### 對位規則（`lib/moLineMatch.ts`）

只有 `MOT`／`MOS` 是行號制。剝掉批次／補印後綴（`-8MM-0819`、`-L1`、`-1`）後，取**長度 ≥5 的最後一個數字段末兩碼**。

- `MOT26070200902` → `02` → 第 2 行
- `MOT260806-120202-73801` → `01` → 第 1 行（**取第一段 `MOT260806` 的 `06` 會全錯**，SOA 訂單的編號格式是特例）

`MOM` 不列入——那是**集單合併生產**（多張訂單的同一品項集中做），編號是流水號不是行號。

實測 1,828 張行號制工單，命中 1,821、不符 7，準確率 **99.62%**。

## 順帶完成：塔台現場進度改為自動同步

原本 `sara_wip_records` 是人工匯出 CSV 再匯入，資料停在 2026-07-31。本次改為直接打塔台網頁版 API 自動同步。

- 新 `POST /api/sara/wip-sync`（GET 為唯讀預覽）：一次打兩支端點就拿到全廠現況，約 4 秒
  - `/api/project/management/table` → 每批進度、跳站警示
  - `/api/wip/schedule` → 每道已排程工序、現在是否在跑
- 新表 `sara_lot_progress`、`sara_wip_schedule`（見下方 SQL）
- `lib/saraWebClient.ts` 附加 `saraProjects`／`saraWip`／`SaraWipRow`，既有的 `saraFindProjects`／`saraJobsOfLot`（出單表製令查詢用）**未更動**
- 護欄：塔台回空陣列時整輪放棄，不寫入也不刪除，避免登入失敗把現況洗掉

`sara_wip_records`（舊 CSV 快照）保留不動。

## 已知限制

- 塔台排程只列「已排程」的工序，做完的會從排程消失，所以「做到哪一站」要看批的進度百分比
- 被刪除的訂單行在 ARGO 已查不到，人員與時間退回用「該單最後異動」推得，介面標 `*`
- 對位若只有末碼吻合或只有料號吻合，會標示 ⚠ 提醒對應關係不完全可信，不直接當結論
- 偵測每 5 分鐘一輪，最新異動最多晚 5 分鐘出現
