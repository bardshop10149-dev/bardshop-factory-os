# 採購專區：備註字數上限放寬、常平出貨備註不再被切斷 (2026-09-21)

## 本次更新重點

> Snow 回報「後面備註的字數好像有限制，導致一些文字被卡掉」。
>
> 查下來根因是追蹤列表備註輸入格的 `maxLength={500}`：**HTML textarea 的 maxLength 是「靜默」擋字的**
> ——打到上限後畫面毫無反應，游標照樣閃、也沒有任何提示，使用者只會覺得「後面的字被系統吃掉」。
> 因為當下就發現不對、沒有存檔，資料庫裡反而找不到 500 字的紀錄（實查 3,138 筆備註，最長僅 212 字），
> 這也是為什麼從資料面看不出異常。
>
> 調整三點：
> 1. 上限 500 → **2000 字**（前端與 API 同步放寬；DB 欄位本來就是 text 無上限）。
> 2. 剩餘 100 字內開始在輸入格右下角顯示「剩 N 字」（到頂顯示紅字「已達上限」），
>    限制不再無聲無息。
> 3. 自動長高上限 240px → **420px**，長備註不必拖拉就看得完。

## 技術

- `app/purchasing/page.tsx`：新增 `NOTE_MAX_LEN = 2000`，NoteCell 外層改包 `relative` 容器
  以放置計數器；自動長高上限提高到 420px。
- `app/api/purchasing/status/route.ts`：`NOTE_MAX_LEN` 500 → 2000。
  **兩處必須一起改**——只放寬前端的話，超過 500 字會在儲存時被 API 回 400。

## 驗證

- `npx tsc --noEmit` 0 errors。
- 實查線上資料：`po_line_tracking` 有備註 3,138 筆，最長 212 字、無任何一筆達舊上限，
  確認放寬不影響既有資料；DB 欄位為 `text`，無需 migration。

## 追加：常平出貨備註被切在半句（85 筆）

Snow 指出 `POC2026082001` 有一筆備註被截斷。查證後發現與上面的 500 字上限無關，
是**另一條路徑**：常平出貨同步程式在送進 EIP 前就把出貨文字切掉了。

- **切點**：`C:\Users\User\claude code\changping_ship_sync.py` 的 `ship_date_text: ship_text[:200]`。
  常平會把多批出貨累寫在工作表同一格（例：9/10 那批＋9/14 那批），200 字放不下。
- **實例**：`POC2026082001#10` 存進來 206 字（＝`【常平出貨】` 6 字 + 200 字），
  斷在「共5件43.73kg 顺」——下一批的順豐單號整段不見。
- **影響範圍**：全表 3,138 筆備註中，**85 筆**的【常平出貨】行剛好卡在 200 字上限，
  多數斷在順豐單號中間（等於快遞單號遺失）。

**修正**

- Python：`ship_text[:200]` → `[:800]`（該檔不在本 repo，已就地修改並備份）。
- `app/api/changping-ship/import/route.ts`：`NOTE_MAX_LEN` 500 → 2000
  （與採購備註同一個欄位、同一個上限；原本 500 是第二道會再切一次的閘）。

**⚠️ 上線順序很重要**

同步程式用「內容 hash」判斷要不要重送。改了截斷長度 → hash 變動 → 那 85 筆會在
下一次 23:30 排程自動重送修好。**但 EIP 端必須先部署**：若 Python 已放寬而 EIP 還停在 500，
超過 500 字的那幾筆會被切在 500 存下來，而狀態檔已記錄成「已同步」，之後不會再重送，
等於被鎖在半殘狀態。

→ 請**先合併本 PR 等 Vercel 部署完**，再讓當晚排程跑；若已錯過，部署後手動補跑一次
`python changping_ship_sync.py run --full` 強制全量重送即可。
