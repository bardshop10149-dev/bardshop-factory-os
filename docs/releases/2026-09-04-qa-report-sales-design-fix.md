## 一、送出失敗的原因與修正

**症狀**：按下送出跳出 `送出失敗：[object Object]`，資料沒進資料庫。

**真因**：`schedule_anomaly_reports.qa_category`（異常分類）欄位為 **NOT NULL**，
而這張單刻意不做分類、送出時填 `null` → 被資料庫的 not-null 限制擋下：

```
null value in column "qa_category" of relation "schedule_anomaly_reports"
violates not-null constraint
```

**修正**：改為固定填入分類值 `尚未生產`。既滿足欄位限制，也讓這批單在分類統計中
可辨識，不會混進「其他」。**不需要改資料庫結構**。

**附帶修正**：Supabase 的錯誤是普通物件（含 `message`／`details`／`hint`），不是
`Error` 實例，原本的 `String(err)` 只會印出 `[object Object]`，完全看不出原因。
已改為串接三個欄位顯示，日後同類問題可直接從畫面判讀。

## 二、送出後的「通報內容」

送出成功後，於成功訊息下方顯示通報文字面板，附「📋 複製通報」按鈕（按下顯示
✓ 已複製）與關閉鈕。格式比照已生產異常單的 LINE 通知樣板（`/qa/handling`）：

```
⚠️ 【異常回報｜尚未生產】

📋 相關單號：…
🔢 品項編碼：…
📦 品名/名稱：…
⚠️ 異常原因：…
🏢 回報部門：…
👤 回報人員：…
🏭 處理部門：…
🔧 處理人員：…
🖼️ 附件圖片：N 張
📌 狀態：🟡 待處理
🕐 回報時間：…
```

與已生產版本的差異僅三處，均為實情所需：標題標明「尚未生產」、狀態為 🟡 待處理
（該版為 🟢 已完成）、多一行附件張數；本單沒有「處理紀錄」與「分類」欄故不列。

**實作要點**：組字串必須在「清空表單欄位之前」執行，否則內容會全部變成 `-`
（原流程是送出成功後立即清空所有欄位）。程式碼中已加註解標明此順序不可調換。
複製以 `navigator.clipboard` 為主、`execCommand` 為退路——內網若以 HTTP 存取，
前者會被瀏覽器停用。

## 三、欄位與選單調整

- **部門選單**：濾除生產部（含印刷課、生管課、工程）、包裝部、品保部——尚未生產
  階段與產線無關；美編部、業務部排序置頂。以 `includes` 比對，日後新增
  「生產部-XX」子部門會自動排除。
- **欄位順序**：異常回報／異常處理的部門與人員移至表單最上方，日期、單號、品項次之。
